### B1 🔴 `run_command` 无 `cwd` + cargo 向上找 manifest ⇒ **静默测了 harness 自己**

- **现象**：第 6 步 `cargo test --offline` 的返回是 `Compiling my_agent v0.1.0 (D:\...\my_agent)`、`27 passed`。
  agent 明明只写了 3 个测试，却拿到 27 个通过 + `exit 0` —— 它是一个**完美的假阳性**（看起来成功）。
- **最小复现**：沙箱根没有 `Cargo.toml`；`Cargo.toml` 在**它的父目录**。此时 `run_command("cargo", ["test"])` 的
  `current_dir = scratch` ⇒ cargo **向上遍历**找到 `<repo>/Cargo.toml` ⇒ 在 harness 本体上跑测试。
- **我以为**：`cwd` 固定在沙箱根 ⇒ 命令只影响沙箱（模型也是这么推的，但它把原因说成了「cwd 是 my_agent」，**推断错一半**）。
- **实际**：`cwd` 确实在沙箱根，**但子进程会越界工作**——cargo 能沿父目录找到别的项目，`target/` 也会建在那边。
- **归因**：`工具层`（缺 `cwd` 参数）+ `观测`（回执没写 cwd）。
- **后果链**（比"测错项目"更严重）：
  1. 模型可能据此收工（本次它运气好，第 7 步自己反应过来了）；
  2. `cargo add` / `cargo fmt` / `cargo build` 同理会**改到 harness 的 `Cargo.toml` 与 `src/`**——
     这正是本项目「只读源码」约束的漏洞：沙箱边界在 `run_command` 上本来就不成立（`plan_v0.md` §3.5 已记），
     但**向上找 manifest** 是它的一个具体、零成本触发的实例；
  3. 若无人核对日志，这条会被当成"任务成功"归档。
- **修法（已定，2026-11-02）**：见下方「## 修复方案（V0.5）」——**按三层拆开治**，不在 V0.5 上 OS 沙箱。

### B2 🟠 日志无时间戳 ⇒ 无法区分 run、无法量耗时

- **现象**：`data/run.log` 是 append 模式，多次运行首尾相接；只有 `##### START TASK #####` 分隔，
  **没有任何时间信息**：不知道这次跑的是哪天、每步花了 3 秒还是 3 分钟、`cargo test` 那 3.38s 编译占了多少。
- **归因**：`观测`。
- **要什么**：`Logger::record` 的每条前缀一个时间戳（本地时间或 epoch）+ 每步耗时（`Instant` 差值即可，零依赖）；
  文件 sink 与屏幕可以不同，但**必须同源**（沿用 §3.6.6 已有的原则）。
- **附带**：`LogKind::Answer` 出现空行（模型这一轮只出工具调用时 `content` 为空）⇒ 空 body 直接不记。

### B3 🟡 工具回执缺 provenance ⇒ 模型与读者都会被"看起来对"骗

- **现象**：同一份日志里，模型的 `Thought` 写着「cargo's working directory is the actual tool's directory … CWD is the harness project dir」——
  **与实际不符**（真实 cwd 是沙箱根，是 cargo 自己往上找的）。日志没有记录任何 `cwd`，所以这段错误推断无从对质。
- **归因**：`观测`（+ `model-prompt`：它有推断的自由，但宿主没给对质材料）。
- **要什么**：`ToolResult` 回执里带 `cwd` 与完整 argv（现在 `ToolCall` 的 `info()` 有 argv，`ToolResult` 没有 cwd）。
  判据：**回执要能让第三方复现这条命令**，否则它不是证据，只是叙述。

### B4 ⚪ 小事两件

- `run_command` 无 `cwd` 的连带限制：`cargo run --manifest-path newproj/Cargo.toml` 能绕，但 `./script.sh`、`npm test`、`ctest` 这类**不行** ⇒ 子项目任务的通用缺口。
- `cargo test` 的 stderr 把 harness 的 dead_code 告警一起带进了上下文（噪音，非错误）。

#### #2 的判据（2026-11-02 定，现已落地）

1. **只在「意图 ≠ 事实」时打印**（**取代**早期的“`cwd != 沙箱根`”）—— 三种情况拆开看：
   传了 `sub` 且实际到 `sub` ⇒ 复述无增量；没传⇒根、`""`⇒根 ⇒ 复述缺省值；
   只有 **传了但解析后不同**（`sub/../x` 归一、symlink 重定向、绝对路→相对路）才有增量。
2. **打印“生效值”而非“模型给的值”** —— `cwd: ../` 被拦回根时，回执必须显示它**实际跑在哪里**。
3. **用相对沙箱根的路径**（`cwd: sub`），不写绝对路径 —— 绝对路径 ~25 token/次，而“根在哪”应由 task 开头交代一次。
   实现是 `resolved.strip_prefix(root)`（两边都是 canonical，相对部分**不带** Windows 的 `\\?\` verbatim 前缀）；与 `edit_file` 成功提示同一写法。
4. **命令不必回显** —— `inv.info()`（`model.rs:157`）的 `ToolCall` 行已经有 `program`/`args`，回执再写一遍是冗余；
   *例外*：若将来日志不再逐条记 `ToolCall`，就得回退到“回执自带命令行”。

**落地形态（2026-11-02）**：抽成纯函数 `fn cwd_notice(root: &Path, workdir: Option<&str>, resolved_path: &Path) -> Option<String>`（`tool.rs`，`normalize_path` 下方），
由 `RunCommand` 分支拼在 **`run_res` 之前**（`Executor::run` 的 `truncate_head_tail` 保头 75%，前缀不会因截断丢失）。
两个已踩过的坑：

- **`workdir: "."` / `"./"` 会输出空值回执 `cwd : `**（`strip_prefix` 得 `""`，`display()` 打不出东西）——实测确认。
  **修法必须是「两侧归一」**，只归一右边会把用例 2 弄坏。三种实现实测：

  | 用例 | `workdir` | A 现状 | B 只归一 rel | **C 两侧归一（采用）** |
  |---|---|---|---|---|
  | 1 | `None` | None ✓ | None ✓ | None ✓ |
  | 2 | `Some("")` | None ✓ | **`cwd : .` ✗** | None ✓ |
  | 3 | `Some(".")` | **`cwd : ` ✗** | None ✓ | None ✓ |
  | 4 | `Some("sub")` | None ✓ | None ✓ | None ✓ |
  | 5 | `Some("sub/../x")` | x ✓ | x ✓ | x ✓ |
  | 6 | 绝对路 | sub ✓ | sub ✓ | sub ✓ |

  原因：`""` 与 `"."` 在**输入侧**是两个值、在**事实侧**是同一个目录。
  写法：`fn norm(p: &Path) -> &Path { if p.as_os_str().is_empty() { Path::new(".") } else { p } }`，比时两边都过它；
  或等价地先 `!w.is_empty()` 早退。
  ⇒ **用例 2 与 3 必须成对存在**：只断言其中一条都发现不了这个错。
- **必须用 path 比较，不能用 `to_str()` 字符串比较**：字符串比较下 `"sub/"` 会被误判为“不同”而打出噪音；path 比较会自动忽略尾斜杠。
  非 UTF-8 路径用 `display()`（lossy）而不是静默丢弃。

**六条必测用例**（能直接罩 `cwd_notice`，不需要子进程）—— **已全部落地（2026-11-02，`cargo test` 33 passed）**：

| # | 输入 | 期望 | 它坏的时候说明什么 |

| 1 | `None` | `None` | “不噪音”决定坏了 |
| 2 | `Some("")` | `None` | 空串=根 坏了 |

#### #6 的判据（2026-11-02 定）

**已定（2026-11-02，一步到位）**：**A + B 同时做** —— 既落盘给模型（A），又把全文交给日志（B）。理由：成本差别不在结构而在几十行，
而两件事各修一个真问题：A 修“模型被截断后无法自救”，B 修“日志里也没有全文（复盘时看不到模型没看到什么）”。

**一、`run()` 的返回改成一个结构体**（而不是 `(String, bool)`，也不是把原文叠给所有工具）

```rust
pub struct ToolOutput {
    pub shown: String,        // 模型看到的（截断 + 尾注 + 落盘路径）
    pub full: Option<String>, // 日志用；仅“不可复现”工具且确实截断时 Some，已按 cap 截断
}
```

**哪些工具的 `full` 有意义？判据 = 输出是否“可复现”**

| 工具 | `full` | 理由 |
|---|---|---|
| `run_command` | ✅ | 命令可能非幂等（`init`/`test`/时间戳输出），**过了就永久没了** |
| `list_files` | ✅ | 目录快照，同样不可复现 |
| `read_file` | ❌ | 文件还在沙箱里，日志已有 path + offset，随时可重读 |
| `write_file` / `edit_file` | ❌ | 返回本身就是一行摘要 |

> 一个常被忽略的事实：`list_files` 走的是 `_ => truncate_head(...)` 分支（`tool.rs` 末），**它已经会截断并带 marker**，所以它和 `run_command`
> 是同一类问题（只是没人注意到）。`truncate_head` 的 marker 也带了 `total_lines`/`total_len`，能直接做 `TruncSummary`。

**二、三处改动**

| 层 | 改动 |
|---|---|
| `truncate_head_tail` / `truncate_head` | 签名改借用：`&str` ⇒ `(String, Option<TruncSummary>)`。**否则 `raw` 被吃掉，既无东西落盘也无东西进日志** |
| `Executor::run` | 返回 `ToolOutput`；在 `RunCommand` / `ListFiles` 分支里：截断成功 ⇒ ① 落盘（cap 内）② 尾注附相对路径 ③ `full = Some(cap 后的原文)` |
| `agent.rs` | `logger.record_tool(&out.shown, out.full.as_deref())`；`tool_messages` 只收 `out.shown`（模型看到的仍是有界的） |
| `log.rs` | 新增 `record_tool(shown, full)`：控制台打 `shown` 的长度摘要，**文件打 `full`（有则用，无则 `shown`）**。顺手去掉那个假文案 |

**三、细节**

1. **文件名用内容 hash**（`DefaultHasher`，std 自带）：幂等、同输出同文件、`run(&self)` 不用 `Cell`。
2. **一个 `SPILL_CAP` 常量（2~5MB）同时卡两个地方**：落盘文件与 `full`。否则一次 `cat` 大文件能把 `run.log` 也写爆。
3. **尾注写相对沙箱根的路径**（与 `cwd_notice` 同一通则），禁止 `\?\` 绝对路径。
4. **落盘失败不能把命令判失败**：降级成一行“全文落盘失败（日志已留全）”——而 `full` 仍在日志里，**日志是落盘的后备**。
5. **目录用 `<sandbox>/tmp/agent-out/`**，并在尾注标注“工具生成的临时文件”，避免模型把它当自己写的源码。
6. **清理策略：不做**。hash 命名天然去重，沙箱本身是一次性的。

**验证（五条，大部分无需子进程）**

1. `truncate_head_tail("短")` ⇒ `(原文, None)`；长文本 ⇒ `Some(summary)` 且 `omitted/total_lines/total_bytes` 是**手算值**。
2. 落盘：同内容两次 ⇒ **同一文件名**；文件内容 == 原文；超 `SPILL_CAP` 时文件长度 == cap。
3. 尾注：含相对路径、**不含** `\\?\`、不含沙箱绝对路径。
4. `run.log` 里那条 ToolResult 是**全文**（长度 > `MAX_TOOL_OUTPUT`），而模型上下文里那条仍是截断版。
5. 端到端：`rg --help`（>8000 字节）⇒ 回执带路径；`read_file` 该路径能拿到中间段。

#### #4 的五个必改点（2026-11-02 定，漏一个就变成新的静默错误）

1. **字段名 `workdir`**（不是 `cwd`）：Codex、opencode 两家都用这个词，训练数据里出现最多；`cwd` 是概念，留给回执标签用。
2. **`is_dir` 检查放在 `RunCommand` 分支，不能放 `resolve_in`**：`resolve_in` 有 **3 个调用者**（`ReadFile`/`ListFiles`/`EditFile`，`tool.rs:353/357/372`），
   对它们要求“是目录”直接就把 `read_file`/`edit_file` 搞死。⇒ 共用函数只承担**对所有调用者都成立**的不变量
   （`canonicalize` 成功 + `starts_with(root)`）；单场景约束（是目录 / 是普通文件）在调用点做。
   现有代码已经遵守这个分法（`resolve_for_write` 就是因为写入侧的不变量不同而单独存在）——
   所以不新增第三个 `resolve_dir`，直接在 `RunCommand` 分支里：`if !dir.is_dir() { bail!("不是目录: {p}") }`（仅一处用，不值得包函数）。
3. **错误文案也不能改 `resolve_in` 内部的 context**：那句「无法解析路径 {p} , 可用 `list_files '.'` 查看根目录」是给 `read_file`/`edit_file` 用的。
   workdir 场景需要「**工作目录不存在 {p}**」而 `p` 应是模型给的原参数 ⇒ 由**调用点**用 `.with_context()` 覆盖/补上，不碰共用函数的文案。

   **回执/错误文案通则（2026-11-02 定）**：凡是模型可见的路径，只有两个合法来源 ——
   ① **原参数**（模型自己写的那个字符串，用于“你给的东西不对”类错误）；
   ② **`strip_prefix(root)` 后的相对路径**（用于“实际生效在哪”类回执）。
   **禁止**打印 canonical 绝对路径：Windows 的 `canonicalize` 返回 `\\?\C:\…` verbatim 前缀，模型认不出，且等于把沙箱真实位置暴露给它。
   *例外*：子进程自己的 stdout/stderr 管不了（`cargo` 会把绝对路径打出来）—— 那正是 B1 破案的线索，不屏蔽。

   现状核对（`tool.rs:397-401`）：文案已改为「workdir {} 不是目录！」✓；但仍用 `args.workdir.as_deref().unwrap_or(".")`，
   而 `None` 必然解析为根且必 `is_dir` ⇒ 该 `unwrap_or` 是**死分支**（无害，但别误读成“None 时会报这个错”）。
4. **描述里必须写死三条**：
   - 相对路径**以沙箱根为基准**（不是“上一条命令的目录”）；
   - **每次命令独立，不持久**（上一条的 `workdir` 不会被记住）；
   - **不支持 `cd`**（我们没有 shell，`cd` 会白名单失败）。
   > 第 4.1 条尤其重要：**Claude Code 的 cwd 是持久的**，在它上面训过的模型会默认“上一条的 `workdir` 还在生效”；不显式否定，它第二步就会漏传 `workdir`。
5. **`info()` 也记 `workdir`** ✓ 已落地（`unwrap_or("SANDBOX_ROOT")` 与 env `SAND_BOX_ROOT` 撞名，建议改 `.` / `<根>`）。

**提前知道的副作用**：所有 Arg 都带 `#[serde(deny_unknown_fields)]` ⇒ 今天模型只要写 `workdir`/`timeout`/`cwd` 任一个键都是硬解析错误。
加 `workdir` 修掉最常见那个；`timeout` 还在雷区里，#8 落地时必须顺带加，否则“模型尝试设超时”会得到一条参数非法。

**判据不变**：`workdir` 让正确做法更容易（不用记 `--manifest-path`），但它**不是护栏** —— 模型仍可 `workdir: "."` 在根上跑 `cargo test`；护栏只有审批钩子（#5）。

**残留的命名漂移（未改）**：`run_command(program, args, root: &Path)` 的形参仍叫 `root`，而它现在装的是**已校验的工作目录**（仅用于 `current_dir`）。
建议改名 `cwd`（含函数体内一处），否则下一个读代码的人会把它当成沙箱根。
另：`is_dir` 分支里的 `unwrap_or(".")` 是**死分支**（`None` 必然解析为根且必 `is_dir`），无害但会误导。

#### #3 的判据（2026-11-02 定，含五家调研）

调研表在 `plans/plan_v0.md` 的「五家的日志形态」。三条对我们最硬的共同点：**时间戳每条都有**、**`cwd`/id 冗余存**、**transcript 与 debug 分层**。

| 决定 | 取值 | 依据 |
|---|---|---|
| 两个时钟 | `SystemTime` → run 标识/文件头；`Instant` → 耗时 | 五家时间戳都是 wall clock，但**没人用 wall clock 算 Δ**（会跳变） |
| 粒度 | **每条 `record` 带** `[+12.345s]`（相对 run 启动的 `Instant` 偏移） | 共同模式 ①；约 +10 字节/行，换来“卡在哪”可回答 |
| 顶部横幅 | `task()` 里加 `run <ISO> | cwd=<…> | pid=<…>` | 模式 ②③；append 下这是唯一可靠的 run 边界 |
| 总耗时 | **`Drop for Logger`** 打一行 | `?` 早退/panic 展开都能覆盖；唯一不靠“记得加”的位置 |
| 结构 | 保持 `Logger::record` 是**唯一漏斗** | V1 eval 要 JSONL 时只加 writer，`agent.rs` 一行不改 |
| 时间格式 | **采用 `chrono` 0.4.45**（2026-11-02 用户手动引入，决策变更：放弃“零依赖 18 行 UTC 手算”方案） | 实测依赖代价：**Windows 编译图仅 +3 个 crate**（`chrono` + `num-traits` + `windows-link`）；`Cargo.lock` +9 条（`iana-time-zone`/`windows-core` 等是其它 target 的条件依赖，本平台不编译）。实际使用：`DateTime::<Utc>::from(system_time).to_rfc3339_opts(SecondsFormat::Millis, true)` → `2026-11-02T02:30:58.707Z`（与 pi 同格式） |

**明确不做（写清触发条件，免以后反复讨论）**

| 不做 | 触发条件 |
|---|---|
| JSONL transcript | V1 eval 需要机器判定时；或想看“同一任务两次 run 的 diff”时 |
| `parentId` 树 / 分支回退 | 需要“回退到第 5 步重跑”时（pi 有，我们没这需求） |
| OTEL / 结构化 telemetry | 多进程/多机器或要接看板时 |
| 日志搬出仓库 | 现在的好处是“和项目一起看/一起 diff”；`Config.sandbox_root` 已让它可配，够用 |

**可选小练**（不挡路）：本地时间方案 B（Hinnant 的 civil-from-days，~15 行）—— 真要“用眼睛对时”时再做。
> 已无用（2026-11-02 引入 `chrono` 后）；保留作为“std 只能给 epoch 秒”的参考：实测 `SystemTime` **不实现 `Display`**，
> `Debug` 输出是 `SystemTime { intervals: … }`；手写 UTC 换算（~18 行）已实测与 `date -u` 逐字节一致（含 `0` 与 `9999-12-31` 边界）。
> **不可妥协**：耗时用 `Instant`，不用 chrono 的 `Duration`/`TimeDelta`（后者不解决系统时钟跳变）。

**生命周期不变量（2026-11-02 补）**

`Logger` 的三个字段是**单 run 绑定**的（`file` / 基准时钟 / 启动 wall time），所以：

| 场景 | 能不能用 | 依据 |
|---|---|---|
| 一个进程跑一个任务（现状） | ✅ | — |
| 一个进程**顺序**跑多个任务（将来 REPL） | ✅ | `task()` 重新装弹计时字段 ⇒ **每个 task 独立计时**（这就是那两个字段用 `Option` 的真正理由，不是缺陷） |
| 一个进程**并行**跑多个任务 | ❌ | **不是 `Logger` 结构挡的**，是调用方给了同一个文件路径。真要并行：一个 run 一个 `Logger` + 一个文件（现形状已满足），不需要改结构 |

两条使用约束：

1. **`record()` 在 `task()` 之前调用时不能 panic** —— 计时字段是 `Option`，`if let Some` 天默跳过前缀即可。
2. **`Drop` 与“清空计时字段”是开关关系，不是矛皾**（2026-11-02 修正）：
   `record(TaskResult)` 里先取 `instant_time()`（该行前缀 = 本次总耗时）再 `stop_timer()` 清空 ⇒
   `Drop` 看到 `None` 就什么都不打（正常路径已有总耗时）；看到 `Some` 就打“**未正常结束 | 耗时 X**”。
   ⇒ **正常路径靠 TaskResult 那行，异常路径靠 Drop，两者不重叠**。
   但 `start_timer()` 目前是**无条件覆盖**：将来若 REPL 复用同一个 `Logger`，上一个 task 异常结束时会被下一个 task 静默覆掉 ⇒
   应在重装前先判 `Some` 并打一行“上一任务未正常结束”。

   **Drop 覆盖不到的情况**（一次说清，免得以后误信）：`std::process::exit()` / `abort()`、`panic = "abort"` 的 profile（现仓库未设，默认 unwind ⇒ 会跑）、
   SIGKILL / 断电。⇒ Drop 是“尽力而为”，不是保证；且 **`drop` 里不能再 panic**（unwind 中 panic ⇒ abort）。

3. **`emit` 里的 `println!` 是个雷**（2026-11-02 实测）：stdout 管道一关（`./bin | head -1`），`println!` 直接 panic：
   `failed printing to stdout: 管道正在被关闭。 (os error 232)`。若这发生在 `Drop` 里（= unwind 中）⇒ **abort**。
   ⇒ `emit` 应改 `let _ = writeln!(io::stdout().lock(), "{console_text}");`（与文件侧已有的 `let _ =` 对称）。

4. **`LogKind` 不收录“日志器自己的事件”**（2026-11-02 定，与 C++ 析构 noexcept 同一原理）：
   `LogKind` 的语义是“**这话是谁说的**”（Thought/Answer=模型；ToolCall/ToolResult/Error/TaskResult=引擎/工具）——
   而“本次 run 没正常结束”是**日志器自己的收尾**，不是引擎的发言 ⇒ 不应占一个变体（否则 `match kind` 里多一支死分支，且每个新 `match` 都要为它写分支）。
   ⇒ **删掉 `LogKind::Panic`，Drop 里直接拼一行自己的文本**（可复用 `emit`，但格式化自己写），不调 `record()`。
   C++ 类比精确版：Rust 不是“析构默认 noexcept”，而是 **unwind 中再 panic ⇒ abort**（double panic）；
   非 unwind 时的 `Drop` panic 只是普通 panic。结论相同：**析构路径上不能有任何可能 panic/返回 `Err` 的操作**（所以 I/O 全写 `let _ =`）。
   *注*：想“复用 record”本身不是错 —— 错的是 `record` 链路上有 `println!`；两者都该改，但删枚举变体是更根本的那一步。

**可选但不便宜（触发条件未到，先不做）**：把白名单从 **program 级** 细化到 **subcommand 级**
（`cargo check\|test\|build\|run` + 校验 `--manifest-path` 在沙箱内；`rg` 必须带显式路径）——
能挡 90% 的"参数乱来"，但要写一大堆参数解析。**触发条件：模型真写坏一次东西**。

**明确不做**：OS 级沙箱（→ V3）· wasm 沙箱（→ 它是**插件**沙箱，换不掉 `cargo`；触发条件："我开始执行不完全信任的代码了吗"）。

#### 布局探针（2026-11-02 实测，**否证了 `[workspace]` 桩**）

四种布局实测对照（均在 `tmp/` 与 `%TEMP%` 下临时搭建，跑完已删）：

| 布局 | 根部跑 `cargo test` | 子项目 `--manifest-path` | 其它 |
|---|---|---|---|
| **现状**：`scratch` 在仓库内、无桩 | 🔴 静默测 **`my_agent`**（`27 passed`） | ✅ | B1 本体 |
| **`[workspace] members = []`** | ✅ `error: … The manifest is virtual, and the workspace has no members` | 🔴 **坏**：`current package believes it's in a workspace when it's not` | 🔴 `cargo new` 会**改写桩**（`Adding newproj as member of workspace`）⇒ 护树自动失效 |
| **桩 + `exclude = ["*"]`** | ✅ 同上（仍报错） | 🔴 **仍然坏**（`exclude` 没起作用） | 🔴 `members` 依旧被写入 |
| **D：root 做真 package（dummy crate）** | ⚠️ 跑 dummy 自己的 1 个测试（**静默但不伤源码**） | ✅ | `cargo new` 不再改写任何东西 |
| **A：沙箱移出仓库** | ✅ `error: could not find Cargo.toml in … or any parent directory` | ✅ | 唯一同时「报错正确 + 子项目可用」 |

**结论**：

1. **桩不可用** —— 它不是「报错更强」，而是「先把子项目搞死，然后被 `cargo new` 改成静默成功」。
   原因：`members` 为空 ⇒ 子包「认为自己在 workspace 里但不是 member」；而 `cargo new` 会主动把新包写进 `members`。
2. 排序：**A（移出仓库） > D（dummy package） > 现状**，桩**不入选**。
3. A 的代价只是「改缺省值与文档」（`SANDBOX_ROOT` 缺省值 + `AGENTS.md` / 任务文案里的 `scratch`）；
   若要坚持保名 `scratch`，可用指向仓库外的 junction（`Executor::new` 会 `canonicalize`，父目录遍历就落在仓外）——但会引入 Windows junction 新变量，V0.5 不做。
4. D 的残留风险：**假阳性从「改自己源码」降级成「测了个空壳」**，依旧不是正确的错误信号。

### 约定（替代布局修复）：沙箱内不跑「会向上寻找项目根」的工具

背景：只要沙箱在仓库内，**任何会向父目录遍历找“项目根”的工具**都会落到 `my_agent` 上。沙箱里跑什么项目，不是修复手段，但它能决定**撞不撞车**。

| 工具 | 是否向上遍历 | 当前状态 |
|---|---|---|
| `cargo` | ✅ 找 `Cargo.toml`（B1 的本体） | 在白名单里，**不可能移除**（修 Rust 是主任务）⇒ 残留风险永存 |
| `git` | ✅ 找 `.git` ⇒ 在沙箱里跑 `git status` 会报告**真实仓库**，`git add` 会动真仓 | 已在白名单外（正确，**不要加进来**） |
| `npm` / `npx` | ⚠️ `npx` 向上找 `node_modules`；`npm run` 多数情况只认 cwd | 待实测 |
| `uv` / `pip` | ⚠️ project discovery 会向上找 `pyproject.toml` / `uv.lock` | 待实测 |
| `python` / `node` 本体 | ❌ 无遍历概念 | — |
| `rg` / `jq` / `yq` | ❌ 只处理给定路径 | 在白名单里，安全 |

**硬规则：新增 `ALLOW_CMD` 前，先跑 B1 的探针模板** —— 在一个“父目录有别的项目”的目录里跑一次该工具的典型命令，看它是否读到沙箱外的东西。一分钟成本，换一整类 B1。

**约定（用户 2026-11-02 定）**：今后的 dogfooding 任务改用语料（**uv/Python 或 npm/NodeJS 项目**），不再用 Rust 项目 ⇒ 不会与真项目打架；
Rust 项目只在 `scratch/my_api` 副本（V0 验收靶场）上跑，且仍用 `--manifest-path`。

**残留风险（写在还账里，不假装没了）**：模型若仍在沙箱根跑 `cargo test/add/fmt`，仍可能写 `my_agent/target/` 甚至改到 `Cargo.toml`/`src/`；
可见化只能靠清单 **#2（回执带 `cwd`）**，拦截只能靠 **#5（审批钩子）**。

### 验收判据（V0.5 退出）

- 同一个任务重跑：日志里每条命令都能看到 `cwd`，且**模型不再把 harness 的输出误认为自己的结果**（B1 的错误描述可被立即对质）；
