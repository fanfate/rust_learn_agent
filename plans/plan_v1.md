## 0. 一句话

**V1 = 让 agent 能连续跑多步真实任务、可中断、可观测。**

不是"功能更多"，是"从能跑一次到能反复跑同一件事两次并比较结果"。

## 5. 阶段 1 · 可观测 + 可重复

> **重定义（2026-11-11）**：原为“尺子（eval）”。eval 只为回答“改 prompt 变好还是变坏”，而**优化 prompt 不是本项目的学习目标**（随便找个成熟 agent 都能做）；且它的三个前提（固定采样 / 稳定任务集 / 每任务干净 root）现在一条都没有 ⇒ eval 移入 §9，阶段 1 换成三件贴学习目标的活。

| # | 事项 | 为什么在这个位置 |
|---|---|---|
| 1 | **`Usage` 进 `ChatResponse` + `RunReport`**（`run_agent` 返回步数/工具调用数/usage/结束原因） | 阶段 2 的裁剪阈值靠它；且逼人说清“一次 run 到底产出了什么”。**注意：`Usage` ≠ eval**，它不需要任何 eval 框架 |
| 2 | **假 client 三分支**（`VecDeque<ChatResponse>`，离线 `cargo test`） | 直接收尾 / 一次工具调用后收尾 / 工具报错回灌后仍能收尾 —— 这是“agent 循环”的全部语义，现在**零覆盖**（43 条全在 `tool` suite） |
| 3 | **REPL 回路**（≈15 行，`plan_tui.md` 方案 D） | 换任务不用改代码、不用重编译。dogfooding 频率↑ = 发现断点频率↑（Run #1 的四条断点就这么来的）。argv 被它包含，不必单独做。**顺带产出**：`clear_tmp()` 从 `Executor::new`（`tool.rs:561`，`agent.rs:33` 每次 run 都构造）挪到**进程启动一次** —— 否则 REPL 第二轮会清掉第一轮的落盘文件，而历史里还留着那个路径 ⇒ 模型 `read_file` 扑空 |

- **[定]** `Usage` 形状有实测报文（`plan_v0.md:4619` / `:4674`）：`prompt_tokens` / `completion_tokens` / `total_tokens` + `prompt_tokens_details.cached_tokens` + `completion_tokens_details.reasoning_tokens`。后两者是阶段 2 与“thinking 成本”的唯一量化出口。
- **[判据]** 假 client 的 seam 形态：`async fn` in trait + 泛型（`run_agent<C: ChatClient>`），**不用 `dyn`**（V1 不需要运行期换实现）⇒ 避开 E0038。这条同时也满足「**实现** ≥2 个才抽 trait」，因为假 client 是真写出来的第二个实现。
- **[判据]** `RunReport` 里每个数字必须由**循环自己产出**，不能事后解析日志（日志给人看、格式会变、还会被 8000B 截断）。
- **[判据]** 假 client 的 `VecDeque` 空掉时 `panic` 并带上“第 N 步” —— 把“循环多调了一次”变成硬失败。
- **[删去（2026-11-11）]** 任务集来源 / 指标三选几 / 机器可判判定 / 任务集规模：随 eval 一并移出。

## 6. 阶段 2 · 上下文裁剪

- **[定]** 4 条不变量（`plan.md:343` 起）：裁剪单位是 **turn**（`Assistant{tool_calls}` + 紧随的 `Tool` 必须整组增删）· `system` 永不裁 + 补「较早 N 轮已省略」· `reasoning_content` 回灌**必须实测**（DeepSeek 与 OpenAI 规则不一致，别凭记忆）· **压缩不在 V1，它是策略链第 3 档**：① 旧 tool 结果瘦身（确定性、免费）→ ② 丢弃最旧 turn（确定性、原文还在日志）→ ③ **摘要替换**（花一次完整上下文、**不可逆**）。
  ⇒ 先做 1+2 不是因为“压缩难”，而是**压缩的前置（turn 分组 + 边界选择 + 不变量测试）就是 1+2 的全部内容，且 100% 复用**。反之先做压缩 = 同时调不变量和摘要质量。
- **[实测 · pi 1.5.2 `core/compaction/`]** 压缩的坑全在**边界**，不在算法：`reserveTokens = 16384`（阈值得靠 usage 实测定）· 摘要请求**可能比被摘要的内容还大**（“make the summarization request larger than the context it summarizes” ⇒ 必须先剔块）· 摘要模型**会尝试调工具**（turn-prefix / branch / 普通三处都显式抛错）· `Thinking is omitted` · 旧 tool 结果先被截断（“Full content is not needed for summarization”）· 另有 `branch-summarization.js`（分支属 V2 的会话结构，不是压缩的替代品）。
- **[待]** 阈值怎么定 ⇒ 依赖阶段 1 的 `usage` 数据。"占上下文的百分比"比"消息条数"可信。
- **[待]** 建模：`Vec<Turn>`（类型承载不变量）vs 运行期 `drain` 前做断言。`plan_v0.md` §3.7.2 讨论过 `enum Turn<'a>`。
- **[判据]** 裁剪正确性的测试方式：**构造一个"只删一半就必然报 400"的历史**，断言不会产生 `tool_call_id` 悬空——这是"编译器一声不响"型，必须靠测试钉。

## 7. 阶段 3 · 流式 + 取消

- **[定]** 四块拆解与两条实测结论（chunk 边界 ≠ 行边界；单独 `from_utf8_lossy` 再拼接 = 不可恢复）见 `plan.md:5.1`，不复述。
- **[定]** 边界：content 增量打印 · `tool_calls` 按 `index` 累积 · 行/UTF-8 双缓冲 · Ctrl-C 取消。
- **[定]** 不做：断线重连 / `id` 去重 / `retry` 退避 / 自定义 `event:` 类型。
- **[待]** `trait LlmClient { async fn stream(..) }` 撞 **E0038**（已撞过一次）⇒ 大概率回到 enum 分发，或把 `stream` 作为**关联类型/`Box<dyn Stream>` 返回值**。
- **[待]** `Executor::run` 的返回形态：现在返回 `String` + 事后 `truncate_head`；边收边打之后**事后截断失效** ⇒ 需要"边收边决定要不要继续打"。
- **[判据]** 取消的判据不是"能中断"，而是**中断后状态干净**：子进程被杀（复用 `kill_process_tree`）、历史不被写半个 tool 结果、日志有明确的中断标记。

## 8. 阶段 4 · grep / Skill（可插空，grep 优先于 Skill）

> **定位校正（2026-11-02）**：`plan.md:346` 原声执行顺序把 grep 排在 **dogfooding 之前**，实际狗粮时跳过了它。归因：**Run #1 的四条断点里没有一条是“缺 grep”**（B1=cwd、B2=时间戳、B3=provenance、B4 是两件小事）⇒ 它不是 V0.5 的修复项，而是 **V1 的能力扩展**。`plan.md:357` 也早已把它标为“第二档”。

- **grep**：四个设计点已定（`plan.md:357`）——输出契约 `path:line:content`（行号 1-based，与 `read_file` 的 `offset`、cargo 的 `file:line:col` 对齐）· **第三种截断策略**（按**匹配数**封顶 + 报总数 + 指路“收窄 pattern/path”）· 跳过要计数（二进制/非 UTF-8/超大/被忽略目录，静默跳过 = 谎报无匹配）· 落地后**从 `ALLOW_CMD` 删掉 `rg`**（单一真相源）。
  - **⚠️ 硬前置（阻塞项）**：依赖（`ignore` + `grep-regex` + `grep-searcher`，或手写 `regex`+`ignore`）必须先 `cargo add --dry-run` 核实版本，**并等确认**（`AGENTS.md` §0 第 5 条：不引入依赖前先说明理由）。
  - **设计约束（与阶段 3 的交互）**：按条数封顶必须实现为一个**独立小函数**（在 `Vec<Match>` 上封顶），**不要扩 `Truncation`**——后者是字节窗口 `{head_end, tail_start}`，既不表达“条数”，也正好是流式阶段要重做的东西；先扩一次等于白改。
  - **判据缩水**：`plan.md:357` 引的三条判据里，“**要权限粒度**”现在**不成立**（审批钩子已移出 V0.5/V1）⇒ 做 grep 只剩两条真理由：**要行号**、**要按条数截断**（后者 `rg` 变不出来：它只有字节/行窗口，且超 8000B 就走落盘）。
- **Skill**：≈1~2 小时，`list_skills` ≈ `list_files` + 过滤、`read_skill` ≈ `read_file`。它同时是上下文管理的**最小实验载体**（比历史裁剪好上手、能立刻观察）。
- **[判据]** grep 先做还是 Skill 先做：**grep 先**——它直接影响 eval 任务里的“模型能不能高效检索”，而 Skill 只影响 prompt 预算；且 grep 落地后 `ALLOW_CMD` 少一个 `rg`，越晚做越要多维护一处。
- **[事实] prompt 是引导，工具层才是强制**：别的 agent 里观察到“在 `AGENTS.md`/`CLAUDE.md` 里指定 `rg`，模型就仍然用 `rg`，即使有自定义 grep 工具” ⇒ 只改 prompt 不删 `ALLOW_CMD` 里的 `rg`，模型大概率继续 `rg`。反之，白名单本身有个**非安全价值**：它让工具面**确定**（沙箱里没 `python` 时，白名单把“程序不存在”变成明确错误 + 可用列表）⇒ 即使将来上沙箱，也未必该删白名单。详见 `v0.5-breakpoints.md` §#5 裁决的“白名单的两个真问题”。

## 9. 明确不做（及触发条件）

| 项 | 触发条件 |
